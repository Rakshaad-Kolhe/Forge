# Forge V2 — Worker Registration & Heartbeat Specification

This document defines the architectural design, lifecycle states, storage responsibilities, and operational guarantees for **Worker Registration and Heartbeat Coordination** in Forge V2.

---

## 1. Core Objectives & Problem Statement

In a distributed CI/CD engine, worker processes execute arbitrary containerized or bare-metal tasks across heterogenous compute nodes. To coordinate execution safely:

1. The system must know **what workers exist** and **what capabilities they report** (executors, CPU cores, RAM, GPU accelerators).
2. The cluster must determine **which workers are currently alive** in real-time.
3. Node crashes, network partitions, and ungraceful terminations must be detected promptly without saturating the primary relational database.
4. Historical records of workers must be preserved for auditability and post-mortem analysis.

---

## 2. Architectural Separation: Durable Registry vs. Transient Liveness

In accordance with **ADR-002 (PostgreSQL as Authoritative Source of Truth)** and **ADR-003 (Redis for Transient Coordination)**, Forge strictly bifurcates worker responsibilities:

```text
┌───────────────────────────────────────────────────────────────────┐
│                       Distributed Workers                         │
└────────┬──────────────────────────────────────────────────┬───────┘
         │ 1. Registration / Deregistration                 │ 2. High-Frequency Heartbeat
         │    (Infrequent: boot, drain, shutdown)           │    (Every 5-15s, lightweight)
         ▼                                                  ▼
┌───────────────────────────────┐                  ┌───────────────────────────────┐
│          PostgreSQL           │                  │             Redis             │
│   (Authoritative Registry)    │                  │      (Transient Liveness)     │
├───────────────────────────────┤                  ├───────────────────────────────┤
│ • Table: `workers`            │                  │ • Key: `forge:worker:{id}:hb` │
│ • Durable identity (workerId) │                  │ • Expiring string (TTL 15s)   │
│ • Hardware resources & specs  │                  │ • Zero database I/O on tick   │
│ • Executor capabilities       │                  │ • Auto-expires on crash       │
│ • Preserved indefinitely      │                  │ • Ephemeral state only        │
└───────────────────────────────┘                  └───────────────────────────────┘
```

### PostgreSQL: Authoritative Durable Worker Registry

- Persists worker identity, registered status, hostname, capabilities (`executors`), and hardware capacity (`resources`).
- Writes happen **only** upon initial registration, administrative updates, or graceful deregistration.
- Stale, crashed, or disconnected workers are **never deleted** from PostgreSQL.

### Redis: Transient Liveness Coordination

- Stores ephemeral heartbeat markers using native TTL expiration (`forge:worker:{workerId}:heartbeat`).
- Heartbeats are renewed periodically (e.g. every 5s with a 15s TTL) using atomic Redis `setJson(key, val, { ttlSeconds })`.
- **Zero database queries** are generated by periodic heartbeat ticks, preventing connection exhaustion and disk write amplification on PostgreSQL.

## 3. Worker Lifecycle & Liveness State Machines

The worker coordination layer distinguishes between **Lifecycle Status** (administrative and operational intent) and **Liveness State** (physical real-time connectivity).

### Worker Lifecycle Status (`WorkerStatus`)

```text
     ┌──────────┐
     │ STARTING │ (Booting, warming caches, initializing executors)
     └────┬─────┘
          │
          ▼
      ┌───────┐      Drain Request      ┌──────────┐
      │ READY │ ──────────────────────► │ DRAINING │ (Finishing jobs, rejecting new work)
      └───┬───┘                         └────┬─────┘
          │                                  │
          │ Graceful Shutdown                │ Graceful Shutdown
          ▼                                  ▼
     ┌─────────┐
     │ OFFLINE │ (Terminated, unregistered, or stopped)
     └─────────┘
```

| Status     | Meaning                                                                             |
| :--------- | :---------------------------------------------------------------------------------- |
| `STARTING` | Worker process is booting and initializing local execution runtime.                 |
| `READY`    | Worker is fully operational, emitting heartbeats, and available for job allocation. |
| `DRAINING` | Worker is finishing active jobs; the scheduler must not assign new jobs to it.      |
| `OFFLINE`  | Worker has gracefully terminated or been explicitly decommissioned.                 |

### Transient Liveness State (`WorkerLiveness`)

```text
┌───────┐         Heartbeat TTL Expires (Silence / Crash)         ┌───────┐
│ ALIVE │ ──────────────────────────────────────────────────────► │ STALE │
└───────┘ ◄────────────────────────────────────────────────────── └───────┘
                     Heartbeat Received (Revival / Reconnect)
```

| Liveness | Condition                                                                          |
| :------- | :--------------------------------------------------------------------------------- |
| `ALIVE`  | Active heartbeat key exists in Redis with remaining TTL > 0.                       |
| `STALE`  | Durable record exists in PostgreSQL, but Redis heartbeat key is absent or expired. |

## 4. Key Schemas & Data Structures

### PostgreSQL Table: `workers`

```sql
CREATE TABLE IF NOT EXISTS workers (
  id             VARCHAR(128) PRIMARY KEY,
  status         VARCHAR(32)  NOT NULL DEFAULT 'READY',
  hostname       VARCHAR(255),
  executors      JSONB        NOT NULL DEFAULT '[]'::jsonb,
  resources      JSONB        NOT NULL DEFAULT '{}'::jsonb,
  registered_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),

  CONSTRAINT chk_workers_status CHECK (
    status IN ('STARTING', 'READY', 'DRAINING', 'OFFLINE')
  )
);
```

### Redis Key Convention & Payload

- **Key**: `forge:worker:{workerId}:heartbeat`
- **TTL**: Configured via `workerHeartbeatTtlSeconds` (default: 15s)
- **Value**:
  ```json
  {
    "workerId": "worker-node-01",
    "timestamp": "2026-09-07T05:20:00.000Z",
    "status": "READY"
  }
  ```

## 5. Operations & Workflows

### 1. Worker Registration (`registry.register`)

1. Validates input (ensures `cpuCores > 0`, `memoryBytes > 0`, non-empty `executors`).
2. Performs idempotent upsert (`ON CONFLICT (id) DO UPDATE`) in PostgreSQL.
3. Sets the initial heartbeat key with TTL in Redis.
4. Emits structured log event.

### 2. Heartbeat Renewal (`registry.heartbeat`)

1. Executed by worker background timer every `workerHeartbeatIntervalMs` (e.g. 5000ms).
2. Writes JSON payload to Redis key `forge:worker:{id}:heartbeat` with `EX ttlSeconds`.
3. Does **not** touch PostgreSQL.

### 3. Stale Worker Detection (`registry.getWorker` / `registry.listWorkers`)

1. Retrieves durable worker metadata from PostgreSQL.
2. Checks presence of Redis key via `isAlive(workerId)`.
3. If Redis key is missing or expired, liveness is marked `STALE`.
4. The scheduler can query `registry.listWorkers({ liveness: 'ALIVE', status: 'READY' })` to identify eligible workers.

### 4. Graceful Deregistration (`registry.deregister`)

1. Removes the Redis heartbeat key immediately via `DEL`.
2. Updates PostgreSQL record status to `OFFLINE` and refreshes `updated_at`.
3. Prevents spurious stale timeouts during planned deployments or maintenance.

---

## 6. Non-Guarantees & Explicit Architectural Boundaries

To preserve strict component decoupling:

1. **Heartbeat is NOT a Job Lease**:
   - A worker's heartbeat indicates node liveness.
   - It does **not** grant or extend ownership of a specific job. Job leases are managed independently via job-level lease tokens.
2. **No Job Claiming or Dispatch**:
   - PR 08 implements worker registration and liveness only.
   - Workers do not dequeue from `@forge/queue` or claim execution leases in this PR.
3. **No Execution Sandboxing**:
   - Docker and Kubernetes container runners will be introduced in subsequent execution PRs.
