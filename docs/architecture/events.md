# Forge V2 — Typed Event Architecture (PR 20)

Status: **implemented** (PR 20). Supersedes nothing. Extended by future realtime/transport PRs.

PR 19 made Forge capable of executing work. PR 20 makes that execution **observable** through
a stable architectural event boundary — without building the realtime delivery system yet.

---

## 1. Purpose & non-goals

`@forge/events` defines **what happened** in a job's / worker's lifecycle as a set of typed,
versioned, uniquely-identified events, plus a transport-independent publish/subscribe seam
and one in-process implementation.

It exists so later PRs can add real-time logs, WebSockets, notifications, metrics, tracing,
and ops dashboards **without touching the execution engine**.

**This PR does NOT:**

- implement WebSocket transport, a browser client, or dashboard integration;
- introduce Redis Streams / Pub-Sub, Kafka, NATS, or any external broker;
- add a PostgreSQL event store or an outbox;
- implement event sourcing or reconstruct authoritative state from events;
- claim exactly-once event delivery.

---

## 2. Where events sit in the architecture

```
PostgreSQL   ->  authoritative durable state      (unchanged)
Redis        ->  transient coordination           (unchanged)
Events       ->  lifecycle notification / decoupling   (new, this PR)
```

```
Scheduler / Worker / Execution lifecycle
              |
              v
        createForgeEvent(...)      typed, versioned, id-stamped envelope
              |
              v
        EventPublisher.publish()   best-effort, AFTER the PostgreSQL commit
              |
              v
        EventSubscriber handlers   isolated; no global ordering
```

The event system is conceptually independent of PostgreSQL, Redis, Docker, WebSocket, and
React. Producers depend on the neutral `@forge/events` contract; the contract depends on
nothing in Forge except `@forge/logging` (for the bus's failure diagnostics) and, through
it, `@forge/contracts`.

Dependency directions introduced:

```
apps/scheduler  ->  @forge/events
apps/worker     ->  @forge/events
@forge/events   ->  @forge/logging  ->  @forge/contracts
```

No new dependency points **into** `@forge/events` from `database`, `scheduler`, or `worker`
internals, and there is no circular package dependency.

---

## 3. Source-of-truth rule

Events are **notifications of committed state transitions**, never the state store.

- A subscriber disappearing does not make durable job state disappear.
- An event-publication failure does not roll back or corrupt PostgreSQL.
- Authoritative job/attempt/lease state is still read from PostgreSQL repositories, exactly
  as before PR 20.

Forge remains **at-least-once delivery + idempotent state transitions** (ADR-004). The event
layer inherits that: consumers must tolerate duplicate events (see § Deduplication).

---

## 4. Event envelope

Every event is a `ForgeEventEnvelope<TType, TPayload>` (`packages/events/src/envelope.ts`):

| Field         | Type                     | Notes                                                                    |
| ------------- | ------------------------ | ---------------------------------------------------------------------- |
| `event_id`    | `string` (UUID v4)       | Unique per publication. Immutable. Never derived from `event_type`.   |
| `event_type`  | `ForgeEventType`         | Discriminant.                                                          |
| `occurred_at` | `string` (ISO-8601 UTC)  | Wall-clock construction time. **Not** a causal-order signal.          |
| `version`     | `1`                      | Schema version — always the current `EVENT_SCHEMA_VERSION`.           |
| `payload`     | type-specific            | Only fields useful to consumers, populated from real committed state. |

Optional correlation ids, set where the producing lifecycle can populate them:
`pipeline_id`, `run_id`, `job_id`, `attempt_id`, `worker_id`. These are plain strings
carrying the same values as the branded domain ids (`PipelineId`, `PipelineRunId`, `JobId`,
`JobAttemptId`, `WorkerId`) — the event layer does **not** introduce a new id system.

Field naming is `snake_case`, matching the existing cross-boundary wire convention
(`LogEntry.request_id` in `@forge/contracts`) and keeping the contract stable if it is later
serialized onto an external transport.

Construction is centralised in `createForgeEvent(type, { correlation?, payload }, { now?, eventId? })`.
It stamps `event_id` / `occurred_at` / `version`, freezes the envelope, and does **not**
validate (validation is a separate concern — see § Validation). The `now` / `eventId`
overrides exist only for deterministic tests.

---

## 5. Event identity

`event_id` is generated by `generateEventId()` = `node:crypto.randomUUID()` (v4).

- Forge-generated, never supplied by a caller in production paths.
- Immutable once assigned.
- Not derived from `event_type` — two events of the same type get different ids.
- Suitable for downstream **deduplication** under at-least-once delivery.

This is **not** a claim of exactly-once publication: a producer retrying after a crash
legitimately mints a new id for the re-publication. Consumers dedupe on `event_id` for the
events they actually received, and additionally rely on idempotent handlers.

---

## 6. Versioning

Every event carries `version: 1`.

- **Additive, backward-compatible change** (a new optional field): keep `version: 1`.
  Consumers ignore unknown fields — the zod schemas `.strip()` them.
- **Incompatible change** (field removed/retyped, semantics changed): introduce `version: 2`
  as a distinct shape. Consumers must branch on `version` and must **not** silently
  reinterpret an unknown version — `parseForgeEvent` rejects any `version` other than the
  current one.

No schema registry, no migration framework. Compatibility is a documented contract.

## 7. Event catalog

`emitted` = a real producer publishes it in this PR. `deferred` = contract defined, no
producer yet (the lifecycle does not exist in the codebase).

| Event              | Status     | Authoritative producer                              | Key payload                                                                              | Correlation                              |
| ------------------ | ---------- | -------------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------- |
| `PipelineCreated`  | deferred   | (future API/ingress)                               | `pipeline_id`, `name`, `step_count`                                                     | `pipeline_id`                            |
| `PipelineQueued`   | deferred   | (future API/ingress)                               | `pipeline_id`, `run_id`                                                                 | `pipeline_id`, `run_id`                  |
| `PipelineCompleted`| deferred   | (future run-aggregation service)                  | `run_id`, `status`, `job_count`                                                        | `run_id`                                |
| `JobQueued`        | emitted\*  | Worker — on retry re-queue (`transitionTo('QUEUED')`) | `job_id`, `run_id`, `priority`, `attempt_number`, `next_attempt_at?`                | `run_id`, `job_id`                       |
| `JobClaimed`       | emitted    | **Scheduler** — successful `worker_leases` claim   | `job_id`, `worker_id`, `lease_id`, `lease_expires_at`                                   | `job_id`, `worker_id`                    |
| `JobStarted`       | emitted    | **Worker** — after `RUNNING` persisted             | `job_id`, `attempt_id`, `worker_id`, `attempt_number`                                   | `run_id`, `job_id`, `attempt_id`, `worker_id` |
| `JobLogChunk`      | emitted\*\*| **Worker** — derived post-execution               | `job_id`, `attempt_id`, `sequence`, `stream`, `chunk`, `byte_offset`, `truncated`, `final` | `job_id`, `attempt_id`               |
| `JobSucceeded`     | emitted    | **Worker** — after terminal persist                | `job_id`, `attempt_id`, `worker_id`, `attempt_number`, `duration_ms`, `exit_code`      | `run_id`, `job_id`, `attempt_id`, `worker_id` |
| `JobFailed`        | emitted    | **Worker** — after terminal persist                | ` … `, `failure_kind`, `reason`, `exit_code`, `retry_scheduled`, `next_attempt_at?`    | `run_id`, `job_id`, `attempt_id`, `worker_id` |
| `JobCancelled`     | emitted    | **Worker** — after terminal persist                | `job_id`, `attempt_id`, `worker_id`, `attempt_number`                                   | `run_id`, `job_id`, `attempt_id`, `worker_id` |
| `WorkerRegistered` | emitted    | **Worker** — after `registry.register()` resolves  | `worker_id`, `hostname?`, `capabilities[]`, `cpu_cores`, `memory_bytes`                | `worker_id`                             |
| `WorkerHeartbeat`  | emitted    | **Worker** — after each successful heartbeat tick  | `worker_id`, `status`                                                                  | `worker_id`                             |
| `WorkerLost`       | emitted    | **Scheduler** — per lease reconciled by recovery   | `worker_id`, `job_id`, `lease_id`, `recovery_action`, `dead_letter_reason?`            | `job_id`, `worker_id`                    |

\* `JobQueued` has a real producer only for the **retry re-queue** transition. First-time
enqueue belongs to the API/ingress plane, which does not exist yet.

\*\* `JobLogChunk` events are **derived after execution completes** from the bounded
`ExecutionResult` (PR 19's capped stdout/stderr capture). They are **not streamed live**.
Live streaming arrives with the log-collector / WebSocket PR:

```
Container stdout -> Log Collector -> Forge Event -> transport -> WebSocket -> Browser   (future)
```

### `failure_kind` (on `JobFailed`)

| Value            | Meaning                                                        | `exit_code` |
| ---------------- | ------------------------------------------------------------- | ----------- |
| `FAILED`         | non-zero process exit                                         | the code    |
| `TIMED_OUT`      | wall-clock timeout; container stopped                         | `null`      |
| `LEASE_LOST`     | lease ownership lost mid-execution; container aborted         | `null`      |
| `EXECUTOR_ERROR` | executor threw before producing a result                     | `null`      |

`retry_scheduled` is `true` when `evaluateRetry` scheduled another attempt (the job returned
to `QUEUED`), in which case a `JobQueued` event follows and `next_attempt_at` is set.

### Why the scheduler owns `JobClaimed` and `WorkerLost`

Both the scheduler and the worker can, mechanically, acquire a `worker_leases` row. To avoid
a duplicate event for the same transition, the **scheduler** is the sole authoritative
producer of `JobClaimed` (invariants §13.1 — placement + lease claiming is the scheduler's
job). `WorkerShell.claimJob` is a lower-level primitive and stays silent. Likewise
`WorkerLost` is emitted only by the scheduler's recovery sweep, which observes the
`LeaseRecoveryService` outcome; `NO_OP` reconciliations do not emit.

## 8. `JobLogChunk` constraints

- `stream` distinguishes `stdout` from `stderr`.
- `sequence` is monotonic (0-based) across a single derivation. All `stdout` chunks precede
  all `stderr` chunks — the executor merges capture into two separate buffers, so
  cross-stream interleaving is **not** preserved and is not claimed.
- `byte_offset` is the chunk's offset within its own stream.
- Chunk size is bounded by `DEFAULT_LOG_CHUNK_BYTES` (64 KiB). Boundaries are byte
  boundaries and may bisect a multi-byte UTF-8 sequence; a consumer reassembles a stream by
  concatenating its chunk payloads in `sequence` order.
- `truncated` propagates PR 19's output-cap flag onto every chunk. `final: true` marks the
  last chunk of the derivation. Entirely-empty output produces no chunk events.
- PR 19's output bounds are unchanged.

## 9. Ordering guarantees

**Per-producer logical ordering — GUARANTEED.** `InProcessEventBus.publish()` invokes
subscribers sequentially in subscription order and resolves only after the last settles.
A producer that `await`s `publish(a)` before `publish(b)` therefore guarantees every
subscriber observes `a` before `b`. The worker emits its lifecycle events in this awaited,
sequential fashion, so for one attempt a subscriber sees:

```
JobStarted -> JobLogChunk* -> (JobSucceeded | JobFailed [-> JobQueued] | JobCancelled)
```

and for the cross-component happy path (single job, events published sequentially):

```
JobQueued -> JobClaimed -> JobStarted -> JobSucceeded
```

**Cross-producer / global ordering — NOT guaranteed.** Concurrent `publish()` calls from
different producers (e.g. two workers, or the scheduler and a worker) may interleave
arbitrarily.

**Across workers — NOT guaranteed.** `occurred_at` is a wall clock. Do not treat timestamp
order as causal order.

## 10. Failure model

### Publisher failure

Publication is **best-effort, after the PostgreSQL commit**. Every producer calls
`safePublish(publisher, event, logger)`, which:

- is a no-op when no publisher is configured (events are opt-in);
- catches any error from `publish()`, logs it with event context (`event_id`, `event_type`,
  `job_id`/`attempt_id`/`worker_id` where present), and swallows it;
- never throws, never blocks the caller's control loop (observability invariant §7.3).

### The DB-commit / event-publish window

```
domain transition -> persist authoritative state (PostgreSQL commit) -> publish event
```

The event represents **committed** state. This creates a known, un-hidden failure window:

```
DB commit succeeds
        |
        v
event publish fails   ->   state is correct and durable; the notification is simply lost
```

There is **no outbox** and **no transactional guarantee** binding the commit and the
publication. A durable outbox for reliable publication is future work; PR 20 does not ship a
partial version of it. Consumers that need completeness must reconcile against PostgreSQL,
not rely on having seen every event.

### Subscriber failure — isolation

`InProcessEventBus` invokes each subscriber in its own `try/catch`. A handler that throws or
rejects is **caught, logged, and skipped**; remaining subscribers still receive the same
event. Errors are **not** propagated to the publisher and are **not** retried.

```
event
 |-- subscriber A -> success
 |-- subscriber B -> throws   -> logged, isolated
 |-- subscriber C -> success
```

### Shutdown

`InProcessEventBus.close()` is idempotent. After it: `publish()` rejects with
`EventBusClosedError` (caught by `safePublish` as a best-effort failure), `subscribe()`
throws `EventBusClosedError`, and all subscribers are dropped. `publish()` calls already
past the closed-check run to completion.

### Duplicate publication

The bus does **not** deduplicate. Re-publishing the same `event_id` delivers it again. The
event layer never falsely claims dedup; consumers dedupe on `event_id` + idempotent
handlers.

---

## 11. Deduplication

The contract provides enough for a future consumer to deduplicate: `event_id` is unique,
immutable, and independent of `event_type`. Payloads are deterministic given the same
committed state. No Redis-backed dedup table and no PostgreSQL event store are introduced.

---

## 12. Validation

`packages/events/src/schema.ts` provides zod schemas (`forgeEventSchema` discriminated
union, `forgeEventSchemas` per-type) and `parseForgeEvent` / `safeParseForgeEvent`.

- Rejects: missing/malformed `event_id`, non-ISO `occurred_at`, `version` ≠ current, unknown
  `event_type`, payload not matching its type, missing required payload fields, empty-string
  correlation ids.
- Strips unknown envelope/payload fields (forward compatibility).

`createForgeEvent` does not validate (kept allocation-light for the hot path); validate at
trust boundaries and in tests.

---

## 13. Exhaustiveness

`ForgeEvent` is a discriminated union on `event_type`. `summarizeForgeEvent` switches over
every variant and ends in `assertNever(event)`. Adding a union member without a matching
`case` is a **compile error**. `FORGE_EVENT_TYPES` is the runtime counterpart, and a
contract test asserts it matches the discriminated-union options exactly.

---

## 14. In-process bus is not a distributed transport

```
In-process bus  ≠  distributed durable event transport
```

`InProcessEventBus` fans an event out to subscribers **in the current process only**. It is
not responsible for cross-process delivery, persistence, or replay, and holds no global
singleton — callers construct, own, and `close()` an instance.

---

## 15. Future transport

Later PRs may connect the same `EventPublisher` / `EventSubscriber` seam to:

- a Redis-based transport (Streams or Pub/Sub),
- WebSockets for the web UI,
- a metrics exporter,
- a notification service,
- a tracing backend,

and may add a durable outbox for reliable publication — **without** rewriting producers or
the execution engine, and without binding PR 20 to any particular transport.

---

## 16. Guarantees, stated plainly

```
PostgreSQL   = authoritative state
Events       = lifecycle notifications
```

```
No exactly-once event-delivery guarantee.
No exactly-once job execution.
No global event ordering.
No transactional DB-commit + event-publish atomicity (no outbox yet).
```
